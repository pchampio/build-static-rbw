# Initial source security review — 2026-11-13

## Conclusion and scope

No evidence of intentional credential exfiltration or a hardcoded attacker/analytics endpoint was found in the paths reviewed. **This is not proof of absence, a complete independent audit, or a clean security bill. Known dependency advisories exist.** I do not recommend an unconditional migration until their impact is assessed or fixed.

Reviewed source: [rylos/rbw enhanced, 6ca8ae724ce7aea718a91fff3a34b268d9fcff4d](https://github.com/rylos/rbw/tree/6ca8ae724ce7aea718a91fff3a34b268d9fcff4d). Compared against doy/rbw main at 77464d414a9e41165d5b15f049bee1f0c0f2a982 (merge-base comparison): 51 changed files, about 14,757 added and 1,505 removed lines, including tests/docs. Focused manual static review covered network destinations, authentication and token storage, added encryption/write paths, PIN/biometric/auto unlock, agent key access, attachment download/save, typing and external commands, and dependency provenance. No real vault, master password or API key was used. The initial native musl CI test run on both architectures was subsequently performed; its finding and packaging patch are documented below. No adversarial runtime penetration test, complete transitive-dependency source audit, or formal cryptographic verification was performed.

## Network and credential handling

- [src/config.rs](https://github.com/rylos/rbw/blob/6ca8ae724ce7aea718a91fff3a34b268d9fcff4d/src/config.rs) derives API/identity/notification destinations from configuration. Defaults are Bitwarden US, with EU and self-hosted support. I found no hardcoded fork-author endpoint in executable network paths. The SSO callback is local HTTP; notification connections use the configured server.
- [src/api.rs](https://github.com/rylos/rbw/blob/6ca8ae724ce7aea718a91fff3a34b268d9fcff4d/src/api.rs) sends login proofs, API credentials, bearer/refresh tokens to the configured identity/API endpoints. Normal password login sends a derived password hash, rather than the raw master password. Added edits/folders/attachments encrypt sensitive values before API writes; encryption keys stay client-side in the reviewed paths. This does not mean all metadata is encrypted.
- Attachment upload sends encrypted bytes and encrypted filename/key to the configured server. Attachment download follows a server-supplied absolute HTTP(S) URL (potentially an external storage host). The second download GET does **not** attach the bearer token. This means network access is not restricted to a single configured origin: a malicious server can trigger requests to other HTTP(S) locations, exposing client IP and fetching arbitrary content. Download size is unbounded in memory. These are trust/availability concerns, not observed deliberate password exfiltration.
- Added blocking HTTP clients use default reqwest settings rather than the shared client-certificate setup. This can break new operations on mTLS-protected servers. HTTP self-hosted URLs are accepted; configure HTTPS. No explicit certificate-verification disablement was found in reviewed client construction.
- The primary cipher implementation remains upstream-derived; the new binary attachment format reuses authenticated symmetric encryption. Its test checks roundtrip, tampering and wrong-key rejection. This is supporting evidence, not a cryptographic audit.

## Security-sensitive behavior and findings

1. **Known dependency advisories — requires assessment before trusting the build.** OSV querybatch matched 11 of 378 registry packages in the reviewed lockfile (including optional/platform packages). Important matches include rustls 0.23.35 (TLS state-machine/secret-debug/certificate-decompression/downgrade advisories), rustls-webpki 0.103.15 (distrusted intermediates), rsa 0.9.9 (timing side channel), crypto-bigint 0.5.5 (timing variability), lru 0.12.5 (aliasing and panic-safety memory issues), tokio 1.48.0 (AsyncFd I/O safety), rustix 1.1.3 (xattr initialization), and quinn-proto 0.11.13 (multiple DoS/memory exhaustion issues). daemonize, paste and pin-utils also have maintenance advisories. Lockfile presence does not establish that a vulnerable function is compiled/reachable. Most affected versions are inherited from the compared upstream; lru and paste are additions associated with the TUI. See each release's full JSON/Markdown report for advisory IDs, references and fixed versions. Build scripts preserve the upstream lockfile and do not silently patch dependencies or suppress findings.
2. **Optional remembered master password lowers the local protection boundary.** [src/biometric.rs](https://github.com/rylos/rbw/blob/6ca8ae724ce7aea718a91fff3a34b268d9fcff4d/src/biometric.rs) explicitly documents that a process running as the same user can recover a remembered password from systemd-creds or Secret Service. Polkit does not make that storage inaccessible to same-user malware. NAS contrib helpers keep their decryption key on the same account; they are obfuscation against partial backups, not isolation. None is installed/enabled by the builder or installer change.
3. **Optional soft locking retains vault keys.** [state.rs](https://github.com/rylos/rbw/blob/6ca8ae724ce7aea718a91fff3a34b268d9fcff4d/src/bin/rbw-agent/state.rs) retains keys in memory when PIN/system authentication is enabled and timeout_action is lock. Its key accessor refuses normal use while soft-locked, and reviewed cipher/attachment paths use that accessor. This is a different guarantee from destroying keys. Set timeout_action=forget to discard keys. auto_unlock with a saved password can unlock without a prompt. These features default off; existing upstream-style configuration keeps password unlock. PIN hashes are Argon2-based but short PINs are offline-guessable by a user who reads the file. The agent's five-attempt limit is not offline protection.
4. **CLI attachment export can expose plaintext to other local users.** In [items.rs](https://github.com/rylos/rbw/blob/6ca8ae724ce7aea718a91fff3a34b268d9fcff4d/src/bin/rbw/items.rs), attachment_get creates output without an explicit 0600 mode; with umask 022, a new export can be 0644. Use umask 077 for CLI exports into private directories. TUI write_new_file explicitly uses 0600 and create_new. Opening a decrypted attachment delegates to the host's associated application, and decrypted files remain until their directory is removed/logout where applicable. Do not open untrusted attachments.
5. **Typing/clipboard depend on desktop trust.** Passwords are passed to typing helpers through stdin rather than process arguments, and multiline typing is rejected. Focus can still change during the delay and receive a password in the wrong application. Tabs act as field-navigation keystrokes. Clipboard clearing reduces retention but cannot prevent clipboard managers/history or other desktop clients from capturing the value.
6. **Confirmed memory-lock drop-order defect (patched in these builds).** Initial musl tests failed on both amd64 and arm64 in cipherstring::test_bytes_roundtrip: region::LockGuard panicked on munlock with ENOMEM. In src/locked.rs, Vec declares data before _lock, so after its Drop method zeroizes memory, Rust drops/frees data before dropping the guard. Musl can unmap the allocation first, leaving munlock an unmapped region. This file is unchanged from the compared upstream. patches/0001-unlock-before-free.patch explicitly drops the lock guard after zeroization while data is still alive. This fixes the observed ordering defect without disabling locking or skipping the encryption test. Applied patch contents and hash are bundled in releases; these binaries are latest upstream source plus this explicit patch.
7. **Latest-git is a continuing supply-chain trust decision.** This review covers the named commit only. Future source/dependency build scripts execute during builds and can change behavior. Pinned Actions, read-only isolated build jobs, separate release credentials, locked dependencies and source manifests reduce packaging risks; they do not certify upstream. Release dependency reports are informational and do not block builds on known findings. SHA256SUMS shares the release's trust boundary.

## Suggested migration posture

Keep pinentry-based password unlocking and avoid remember-password, PIN, system_auth and auto_unlock unless their local security model is acceptable. Keep a finite lock timeout. Use HTTPS and trusted server configuration. Resolve/assess the dependency advisories, including the fork-added lru issue, before relying on this for valuable secrets. Consider reviewing each new source commit before triggering a build. The installer change only changes the release source; it does not enable the optional security features, install PAM/polkit rules, run the binary, or migrate/unlock a vault.
